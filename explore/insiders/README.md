# Phase 2 feasibility: officer/director purchase filings

Source: [SEC Insider Transactions Data Sets](https://www.sec.gov/data-research/sec-markets-data/insider-transactions-data-sets), with [table definitions and code list](https://www.sec.gov/files/insider_transactions_readme.pdf). The SEC offers quarterly Form 3/4/5 XML extracts from January 2006 through June 2026. This probe processes the 58 ZIPs from 2012 Q1 through 2026 Q2 (626,289,157 compressed bytes). `sec_quarters.csv` gives each official URL and download size. `pull_sec.py` downloads each quarter, reads the three relevant tab-delimited tables, and deletes the ZIP after processing. `sec_code_p_events.parquet` holds the filtered as-filed transaction rows. The index HTML is retained as `source.html`.

The purchase proxy is non-derivative transaction code `P`, acquired side `A`, a Form 4 or 5 (not an amendment), and a reporting-owner role containing Officer or Director. The SEC defines `P` as **open-market or private purchase**; the bulk code cannot distinguish the two. Thus these are code-P purchases, **not verified open-market purchases**. An event is one issuer CIK, reporting-owner CIK, and filing date; multiple transaction rows are collapsed for event counts. Filing lag uses the earliest valid transaction date in that event and weekdays as business days (holidays are not removed). Invalid or future transaction dates have no lag.

Mapping begins with the SEC issuer CIK and its as-filed ticker and name at the filing. A ticker used by multiple issuer CIKs is quarantined. For the others, the local EODHD active/delisted symbol-list entry must have a normalized name similarity of at least 0.85 to a name filed under that CIK/ticker, an EODHD per-symbol price file must exist, and a price must be present within five calendar days before filing. Ticker equality alone never establishes a map. `event_feasibility.parquet` records every event's mapping status and data-quality flags; `mapping_failures.csv` lists unresolved issuer/ticker pairs by failure type. `name_change_unverified` is a diagnostic bucket for CIKs with multiple filed names that did not pass identity verification; it does not prove a corporate name change. This conservative mapping can exclude genuine issuers.

The local EODHD active and delisted catalogs contain Code, Name, Country, Exchange, Currency, Type and ISIN, but **no CIK or historical shares outstanding**. The local per-symbol bars contain open, high, low, close, adjusted close, and volume; no authoritative split events. Consequently actual market capitalization at filing and the requested <$300M, $300M–$2B, >$2B cap counts are unavailable. As a feasibility substitute, `quality_by_liquidity.csv` groups mapped events by the median of raw close × volume over up to the last 20 available sessions: <$300,000, $300,000–$2 million, and >=$2 million daily dollar volume. These liquidity buckets are **not market-cap buckets**. The catalogs are local snapshots last modified 2026-09-05; their hashes are in `summary.json`. EODHD documents the [delisted=1 US symbol list](https://eodhd.com/financial-apis/delisted-stock-companies-data-2).

For each mapped event, the quality screen requires positive adjusted prices on every SPY benchmark session from 60 sessions before through 120 after the first trading session on or after filing. It separately flags any observed gap exceeding ten benchmark sessions. An adjusted-close change whose absolute value exceeds 80% is provisionally unexplained unless the contemporaneous raw/adjusted-close ratio changes by approximately a common split factor. That ratio is **not proof of an actual split**; the local store has no split calendar, so split coincidence cannot be fully validated. EODHD documents a separate [splits endpoint](https://eodhd.com/financial-apis/api-splits-dividends). Recent filings are right-censored by the price-history end date and correctly fail full-window coverage. No event-window returns or P&L are computed.

Clusters are counted for each issuer and filing date when at least two distinct reporting-owner CIKs appear in that issuer's trailing 30-calendar-day window, including that date. `summary.json` reports both issuer-date instances and distinct calendar dates. The result is a feasibility census, not a test or performance claim.
